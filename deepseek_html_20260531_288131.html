🧠 AGENTIK v5.0 — ESPECIFICACIÓN COMPLETA PARA EL DESARROLLO

ESTADO Activo – Fase 0 en ejecución

VERSIÓN 5.0 (Definitiva)

LICENCIA MIT

Este documento es la única fuente de verdad para el desarrollo de AGENTIK. Todas las decisiones técnicas, reglas, fases y validaciones están definidas aquí. El agente de desarrollo debe seguir este plan al pie de la letra hasta la finalización del proyecto.

📌 OBJETIVO FINAL

Construir un agente autónomo de desarrollo de software con:

  • Memoria persistente (MemPalace)
  • Aprendizaje operativo (Hermes)
  • Inteligencia de código (Codex)
  • Seguridad integrada (Aegis + ZeroClaw)
  • Validación continua mediante x-dd

Agentik debe ser capaz de recordar, analizar, ejecutar, validar y aprender sin perder trazabilidad.

⚡ REGLAS ABSOLUTAS (R1 a R7)

R1
Toda acción relevante genera un receipt.
R2
Toda acción relevante se almacena en MemPalace.
R3
Ningún cambio se considera válido sin aprobación de x-dd.
R4
Ningún módulo puede acceder directamente a otro si existe Event Bus.
R5
La seguridad tiene prioridad sobre la autonomía.
R6
Auto-mejora prohibida hasta Fase 7.
R7
No usar código copiado de proyectos incompatibles con MIT.

🏛️ PRINCIPIOS ARQUITECTÓNICOS (P1 a P6)

  • P1 — Memory First: Toda información relevante debe poder recuperarse posteriormente.
  • P2 — Test Before Trust: Todo cambio debe ser validado mediante x-dd.
  • P3 — Security Before Execution: Seguridad > Funcionalidad > Conveniencia.
  • P4 — Explainability: Toda acción debe responder qué, por qué y con qué evidencia.
  • P5 — Modularidad Absoluta: Los componentes deben ser reemplazables sin afectar al resto.
  • P6 — Event Driven: Los módulos se comunican mediante eventos.

🗺️ ROADMAP OFICIAL (Fases 0 a 8)

Cada fase debe completarse en orden. Una fase se considera terminada solo cuando se cumplan los criterios de aceptación (ver más abajo).

🔹 Fase 0 — Fundación (Ejecución inmediata)

Objetivo: Base mínima del agente: memoria, CLI, x-dd, receipts, observabilidad.

Tareas concretas (orden obligatorio):

  1. 0.1 Fork de MemPalace – Integrar cliente básico en agentik/mempalace/.
  2. 0.2 CLI básica – Comando agentik run "..." que ejecuta comandos del sistema y guarda en MemPalace.
  3. 0.3 Integración x-dd (Adapter) – Métodos run_pipeline, build, qa_review, close_phase.
  4. 0.4 Receipts y seguridad – Generación HMAC-SHA256, almacenamiento en Audit.
  5. 0.5 Observabilidad básica – Logs JSON y métricas internas.

Validación: Cada tarea tiene su pipeline .xdd en tests/pipelines/. Ejemplo para tarea 0.1:

/xdd-start
/agentik run "from agentik.mempalace import Client; c=Client(); c.store('test', wing='Test'); print(c.recall('test'))"
/gate assert salida_contiene "test"
/cierre-fase

Pipeline maestro de fase: tests/pipelines/fase0_completa.xdd que ejecuta todas las tareas.

🔹 Fase 1 — Orquestación

Objetivo: Implementar Event Bus, Context Builder y Agent Orchestrator.

Entregables:

  • agentik/core/event_bus.py – Publicación/suscripción asíncrona.
  • agentik/core/context_builder.py – Pipeline de contexto según especificación.
  • agentik/core/orchestrator.py – Coordinación de tareas y herramientas.

Validación: Pipeline fase1_valida.xdd que prueba publicación de eventos, construcción de contexto y orquestación de una tarea simple.

🔹 Fase 2 — API + UI (Web, Desktop, Mobile)

Objetivo: Exponer API REST/WebSocket y construir interfaces compartidas con React.

Entregables:

  • Servidor FastAPI con endpoints definidos.
  • Proyecto React (TypeScript + Tailwind) con chat y panel de control.
  • Wrapper Electron para escritorio (ejecutable .exe/.dmg).
  • App React Native para Android (APK básico).

Validación: Pipeline que lanza el servidor, envía un mensaje por WebSocket y verifica respuesta.

🔹 Fase 3 — Codex (Inteligencia de código)

Objetivo: Análisis de código Python (AST, grafo de llamadas, impacto).

Entregables:

  • agentik/native/codex.py con tree-sitter para Python.
  • Comando /impact <símbolo> que retorna callers.
  • Integración automática antes de /xdd-build.

Validación: Pipeline que modifica una función, ejecuta build y verifica que el agente muestra advertencia de impacto.

🔹 Fase 4 — Aegis (Seguridad activa)

Objetivo: Detectar vulnerabilidades estáticas (SQLi, XSS, Command Injection).

Entregables:

  • Análisis estático con tree-sitter + reglas.
  • Comando /aegis-scan y bloqueo de pipeline si se encuentra vulnerabilidad crítica.

Validación: Pipeline que introduce una SQL injection a propósito, el agente debe detectarla y detener el flujo.

🔹 Fase 5 — Hermes (Aprendizaje operativo)

Objetivo: Extraer lecciones de fallos repetidos y crear skills.

Entregables:

  • agentik/learning/lessons.py – detección de fallos repetidos, generación de lecciones.
  • agentik/learning/skills.py – registro de secuencias exitosas y ejecución de skills.

Validación: Pipeline que fuerza un fallo dos veces, verifica que se crea una lección; luego repite una secuencia exitosa tres veces y verifica que se ofrezca una skill.

🔹 Fase 6 — Sistema de Plugins

Objetivo: Permitir extensión dinámica sin modificar el núcleo.

Entregables:

  • Registro de plugins en agentik/plugins/.
  • Contrato Plugin con métodos register().
  • Descubrimiento automático de plugins.

Validación: Pipeline que carga un plugin de ejemplo y verifica que sus herramientas estén disponibles.

🔹 Fase 7 — Auto-mejora controlada

Objetivo: El agente puede proponer parches a su propio código, validados con x-dd y aprobación humana.

Entregables:

  • Comando /agentik self-improve.
  • Flujo: oportunidad → parche → branch temporal → x-dd → Aegis → diff → aprobación → merge.

Validación: Pipeline que detecta una oportunidad de mejora, genera un parche, lo prueba y solicita aprobación.

🔹 Fase 8 — Distribución y actualizaciones

Objetivo: Empaquetado y distribución continua.

Entregables:

  • Generación de ejecutables de Electron (Windows, macOS, Linux) mediante GitHub Actions.
  • Generación de APK para Android.
  • Sistema de auto‑actualización (electron-updater + backend de releases).

Validación: Pipeline que descarga la última versión, la instala en un entorno limpio y ejecuta pruebas de humo.

✅ CRITERIOS DE ACEPTACIÓN (por fase)

  • El código compila (no hay errores de sintaxis).
  • Todas las pruebas (pytest y pipelines x-dd) pasan.
  • x-dd aprueba el pipeline específico de la fase.
  • Existe al menos un receipt por cada acción nueva.
  • La evidencia se ha persistido en MemPalace (wing correspondiente).
  • La documentación se ha actualizado (docs/).

🏆 DEFINICIÓN DE ÉXITO FINAL

Agentik será considerado exitoso cuando:

  • Recuerde automáticamente información relevante de proyectos anteriores.
  • Aprenda patrones reutilizables (lecciones y skills) con mínima intervención.
  • Valide todos los cambios mediante x-dd antes de aceptarlos.
  • Detecte vulnerabilidades de seguridad antes de que el código llegue a producción.
  • Mantenga trazabilidad completa (receipts) de cada acción ejecutada.
  • Permita evolución segura mediante plugins y aprendizaje controlado.
  • Sea distribuible como aplicación de escritorio (Electron) y móvil (Android).

📋 INSTRUCCIONES PARA EL AGENTE DE DESARROLLO

  1. Comienza por la Fase 0 y no pases a la siguiente hasta que los criterios de aceptación de la fase actual se cumplan.
  2. Escribe los pipelines x-dd ANTES de escribir el código (desarrollo guiado por validación).
  3. Toda persistencia debe hacerse a través de MemPalace – no uses archivos sueltos fuera del palacio.
  4. Cada vez que modifiques una herramienta, actualiza su pipeline de prueba.
  5. Respeta las reglas R1 a R7 estrictamente. La auto-mejora solo está permitida a partir de la Fase 7.
  6. Documenta cada módulo con docstrings y mantén cobertura de pruebas >80%.
  7. Usa logging estructurado (JSON) para que el sistema pueda auto‑depurarse.
  8. Si alguna ambigüedad surge, prioriza los principios P1 a P6 sobre cualquier interpretación personal.
